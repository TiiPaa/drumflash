Sauvegarder un pattern pendant la lecture fait craquer l'audio

Cliquer « Save » sur un slot P1…P16 transport lancé fait copier et convertir en JSON plusieurs mégaoctets dans le traitement audio : craquement ou coupure quasi certains.

À faireRemplacer refresh_snapshot() par mark_snapshot_dirty() et rétablir la préallocation des slots après l'ouverture d'un projet.≈ 15 min

drum-pattern-vst/src/lib.rs:2288

Détail technique

Problème

Sauvegarder un pattern dans la banque (P1…P16) exécute sur le thread audio un verrou bloquant, un clone profond de la banque et une sérialisation JSON complète. process() traite la requête via deferred_save_slot (lib.rs:2633-2645) → save_pattern_to_slot() → self.params.pattern_bank.refresh_snapshot(), qui fait self.bank.lock() (Mutex bloquant), guard.clone() des 16 slots puis serde_json::to_vec (pattern_bank.rs:1029-1047). Le commentaire de refresh_snapshot interdit pourtant explicitement tout appel « from the audio callback ». Aggravant : après réouverture d'un projet, les Vec<u8> des slots désérialisés n'ont plus la capacité préallouée par PatternSlot::default() (pattern_bank.rs:61-64 ; un slot vide est relu avec une capacité nulle), donc capture() (pattern_bank.rs:192-214) réalloue elle aussi ~165 Ko de p-locks dans le callback.

Pourquoi c'est un problème

Scénario courant : pendant la lecture, l'utilisateur clique « Save » sur un slot de la banque pour garder une variante. Au buffer suivant, le callback alloue et copie plusieurs mégaoctets puis sérialise un JSON où chaque octet des blobs plock/seq-plock/fusion devient un nombre JSON (l'état observé pèse de 0,4 à 9,7 Mo selon la session). Le budget d'un buffer de 256 échantillons à 48 kHz est de 5,3 ms : dropout/craquement audible quasi certain, rallongé si le thread UI tient le même Mutex au même instant (clear_lane_in_saved_patterns / permute_lanes_in_saved_patterns le prennent en bloquant, pattern_bank.rs:993-1017). C'est une violation directe de l'invariant temps réel n°1 de CLAUDE.md, sur un chemin par ailleurs écrit avec soin en try_lock + relance.

Correctif proposé

1) Remplacer l'appel par la variante déjà prévue pour le thread audio (pattern_bank.rs:1019-1024, « safe to call from the audio thread ») ; PersistentField::map() reconstruit alors le snapshot paresseusement quand l'hôte demande l'état (pattern_bank.rs:1070-1071), hors callback :

        drop(bank);
-       self.params.pattern_bank.refresh_snapshot();
+       self.params.pattern_bank.mark_snapshot_dirty();

2) Rétablir la préallocation après restauration, côté thread principal, dans PersistentField::set (pattern_bank.rs:1055-1062) :

for slot in guard.slots.iter_mut() {
    slot.plock_bytes.reserve(MAX_PLOCK_BYTES.saturating_sub(slot.plock_bytes.len()));
    slot.seq_plock_bytes.reserve(MAX_SEQ_PLOCK_BYTES.saturating_sub(slot.seq_plock_bytes.len()));
    slot.fusion_bytes.reserve(MAX_FUSION_BYTES.saturating_sub(slot.fusion_bytes.len()));
}

Test à ajouter : save_pattern_to_slot_is_realtime_safe — restaurer une banque sérialisée contenant des slots vides, puis appeler save_pattern_to_slot(3) à l'intérieur de assert_no_alloc(|| …) (dev-dependency assert_no_alloc) ; vérifier ensuite que snapshot_dirty vaut true et que map() renvoie un snapshot où P4 est occupé.

Un WAV remplacé peut être libéré en plein rendu audio

Sur une lane One-Shot ou Rift, après avoir essayé deux autres fichiers, le premier (jusqu'à 23 Mo) est libéré au coup suivant, dans le thread audio.

À faireConfier l'ancien fichier à une file de retraite vidée par l'interface.≈ 1 à 2 h

drum-pattern-vst/src/synthesis/oneshot.rs:454

Détail technique

Problème

Les voix One-Shot et Rift gardent leur propre Arc<TextureBank> (self.source, oneshot.rs:62, rift.rs:86) d'un coup à l'autre ; le « parking » d'une génération de TexturePool (sample_bank.rs:155-166) ne protège que les références détenues par le pool. Après deux remplacements du fichier d'une lane sans coup entre-temps, la voix détient la DERNIÈRE référence du premier fichier : self.source = source; dans trigger() (oneshot.rs:454, rift.rs:686) le libère sur le thread audio. Même chose quand le kind d'une lane change en lecture : reinitialize_slot() (synthesis/mod.rs:1577-1588, appelé depuis process() lib.rs:2836) écrase la voix par **existing = new_voice; et libère son source.

Pourquoi c'est un problème

Lane One-Shot, transport lancé : l'utilisateur glisse le fichier A (joué au moins une fois), puis auditionne B et C sur la même lane pendant que celle-ci ne rejoue pas (lane mutée, pas de pas sur la page en cours). Au coup suivant, la libération de A — jusqu'à ~23 Mo pour 60 s de stéréo à 48 kHz (USER_TEXTURE_MAX_SECS) — a lieu dans le callback : pic de latence et craquement possibles, au moment précis où l'on promet zéro allocation/libération. La garantie écrite dans CLAUDE.md (§ Lane textures : « the last reference is never dropped on the audio thread ») est donc incomplète.

Correctif proposé

Ne jamais laisser une voix détenir la dernière référence : pousser l'ancien Arc dans une file de retraite préallouée, vidée par le thread UI (le projet utilise déjà crossbeam) :

// DrumSynthesizer ou TexturePool : retire: Arc<crossbeam::queue::ArrayQueue<Arc<TextureBank>>> (capacité 64)
if let Some(old) = std::mem::replace(&mut self.source, source) {
    let _ = self.retire.push(old); // file pleine = drop immédiat, cas dégradé
}

Appliquer le même traitement au source de la voix remplacée dans reinitialize_slot. Test à ajouter : trigger_never_frees_a_texture_on_the_audio_thread — publier A, trigger(), publier B puis C, puis appeler trigger() dans assert_no_alloc(|| …) (qui détecte aussi les libérations) : doit échouer aujourd'hui et passer après correctif.

Chemins réseau des textures ouverts sans contrôle

Un projet ou un preset reçu peut pointer vers \\serveur\… : à l'ouverture, Windows s'y connecte (fuite possible des identifiants) ou Studio One gèle en attendant un NAS absent.

À faireN'ouvrir automatiquement que des chemins locaux ; un chemin réseau seulement sur choix explicite, hors du thread principal.≈ 1 h

drum-pattern-vst/src/user_textures.rs:44

Détail technique

Problème

Les chemins de WAV par lane venant d'un état VST3 restauré (lane-textures-v1) ou d'un preset JSON (user_texture, presets.rs:87 et 106) sont ouverts tels quels, sans aucune validation : FileKey::of() → std::fs::metadata(path) (user_textures.rs:44), puis hound::WavReader::open (synthesis/sample_bank.rs:244). À l'ouverture d'un projet, PersistentField::set (user_textures.rs:230-240) appelle reload_all() qui résout les 14 chemins de façon synchrone sur le thread principal de l'hôte ; même chemin au chargement d'un preset (ui/preset_browser.rs:665-667).

Pourquoi c'est un problème

(a) Sécurité : un projet ou un preset reçu d'un tiers contenant \\hote-distant\partage\x.wav déclenche, sans aucun clic dès l'ouverture, une authentification SMB (ou WebDAV via \\hote@80\…) de Windows vers cet hôte, qui expose le hash NTLMv2 de la session (fuite d'identifiants classique par chemin UNC). (b) Fiabilité, sans attaquant : un projet dont les textures étaient sur un NAS ouvert sur une autre machine attend le timeout SMB (souvent 20 s ou plus) pour chaque lane concernée, en série, sur le thread principal — Studio One paraît gelé à l'ouverture. Mitigation partielle : un projet DAW peut déjà référencer des fichiers audio UNC ; en revanche les presets JSON sont un vecteur propre au plugin.

Correctif proposé

Ne résoudre automatiquement (restauration d'état, chargement de preset) que des chemins locaux ; un chemin réseau n'est accepté que s'il vient du sélecteur de fichiers ou d'un glisser-déposer explicite, et sa résolution se fait hors du thread principal (comme TexturePick).

Test à ajouter : restore_skips_unc_texture_paths — set(vec![Some(r"\\203.0.113.1\s\x.wav".into())]) doit retourner immédiatement avec status(0) == Missing, plus un test unitaire de is_local_path sur \\h\s, \\?\UNC\h\s, C:\a.wav, \\?\C:\a.wav.

L'installation peut laisser un plugin incomplet (c'est le cas sur ce poste)

Si Studio One est ouvert, build.ps1 -Install supprime d'abord le programme de glisser MIDI puis échoue sur le DLL : le build installé n'est plus celui annoncé.

À faireTester le verrou avant de supprimer, installer via un dossier temporaire, comparer les empreintes.≈ 30 min

drum-pattern-vst/build.ps1:121

Détail technique

Problème

L'installation n'est pas atomique : Remove-Item -Path $destPath -Recurse -Force (ligne 121) supprime le bundle installé AVANT la copie (ligne 124), sans vérifier que le DLL n'est pas verrouillé. Si Studio One (ou l'antivirus) tient le DLL, la suppression efface d'abord drum-pattern-midi-drag-helper.exe puis échoue sur le DLL ; $ErrorActionPreference = "Stop" arrête le script avec un bundle à moitié détruit. Constaté sur ce poste le 2026-09-24 : C:\Program Files\Common Files\VST3\drum-pattern-vst.vst3\Contents\x86_64-win\ ne contient plus que le DLL du build 20260923-233248, sans le helper, depuis la tentative d'install du build 235211 (23:53, « install refusée car S1 ouvert », CHANGELOG). Le défaut est masqué par ui/midi.rs:67, qui ajoute en dur env!("CARGO_MANIFEST_DIR")\build\… aux emplacements de recherche du helper, y compris dans le binaire release.

Pourquoi c'est un problème

Après une install refusée, l'utilisateur ferme Studio One et valide « le build » : il teste en réalité l'ancien DLL, et le glisser MIDI ne fonctionne que grâce au dossier de build du poste de dev (helper d'une autre version). Sur toute autre machine (bundle copié, artefact CI), le glisser MIDI échoue (« MIDI drag helper not found »). Pire cas : un verrou antivirus passager pendant Copy-Item, juste après une suppression complète, ne laisse plus aucun plugin installé. test-verification.ps1 ne contrôle pas le helper et ne traite un hash différent que comme un avertissement (ligne 42).

Correctif proposé

Tester le verrou avant de toucher à quoi que ce soit, installer via un dossier intermédiaire, puis vérifier le résultat :

$dll = Join-Path $destPath "Contents\x86_64-win\$vst3File"
if (Test-Path $dll) {
  try { [IO.File]::Open($dll,'Open','ReadWrite','None').Close() }
  catch { Write-Color Red "DLL verrouillé (Studio One ouvert ?) : rien n'a été modifié."; exit 2 }
}
$staging = "$destPath.new"; $old = "$destPath.old"
Remove-Item $staging,$old -Recurse -Force -ErrorAction SilentlyContinue
Copy-Item $bundleDir $staging -Recurse -Force
if (Test-Path $destPath) { Rename-Item $destPath $old }
Rename-Item $staging $destPath
Remove-Item $old -Recurse -Force -ErrorAction SilentlyContinue

Puis comparer les hash des deux fichiers installés au bundle (échec bloquant), restreindre le chemin CARGO_MANIFEST_DIR de ui/midi.rs:67 à #[cfg(debug_assertions)], et faire échouer test-verification.ps1 si le helper manque ou si le hash diffère. Test à ajouter : paramètre -InstallRoot + test CI qui ouvre le DLL cible en exclusif, relance l'install et exige un code de sortie non nul avec les deux fichiers d'origine intacts.

Vue d'ensemble

Architecture

Monolithe Rust compilé en une seule DLL VST3. L'hôte appelle process() (lib.rs), qui fait avancer un séquenceur maître (sequencer/, groove.rs), déclenche les voix DSP d'un pool de 14 slots (synthesis/, 27 voix) et mixe vers une sortie principale et 14 sorties aux stéréo, tout en émettant du MIDI sur le canal 10. L'éditeur egui (ui.rs + ui/) écrit dans des structures atomiques partagées que le thread audio lit sans verrou ; l'état complet est persisté par nih-plug en dix champs versionnés (pattern-v5, sound-settings-v2, plock-v1…). Le registre instrument_registry.rs est la source de vérité des voix et rend l'essentiel de l'UI data-driven. Deux crates amont sont vendorées et patchées : nih-plug (multi-out et restauration d'état sous Studio One) et egui-baseview (glisser-déposer entrant et replanification des repaints).

Points forts

  • Séparation UI/audio rigoureuse : process() est exempt d'unwrap, de format!, de Box::new et de verrou bloquant, à l'exception du défaut critique de ce rapport ; les trois défauts temps réel de l'audit de juillet 2026 (Mutex en mode song, Box::new dans reinitialize_slot, nih_log dans le callback) sont corrigés
  • Registre central qui rend Sound Panel, menus et p-locks data-driven, et dispatch DrumVoiceKind exhaustif sans branche _ : le compilateur refuse une voix incomplète
  • Persistance disciplinée : longueurs vérifiées avant indexation, migrations legacy explicites et testées (pattern v3/v4, banque 8→16, stride des p-locks, filter_state)
  • Robustesse vis-à-vis de l'hôte : sorties aux clairsemées de Studio One gérées par get_mut et add_stereo_aux_sample avec contrôle de longueur, testées

Points faibles

  • Points de couture fragiles entre les trois espaces d'index (slot, kind, voix) écrits en if/else ou match avec repli implicite (générateur, banque d'échantillons du Sound Editor)
  • Garanties temps réel non outillées : aucun test assert_no_alloc, d'où deux défauts d'allocation/libération passés inaperçus
  • Documentation d'architecture en retard d'une ou plusieurs générations d'instruments (CLAUDE.md, README, guide utilisateur, ADDING_AN_INSTRUMENT.md, docs/infrastructure.md)
  • Fork nih-plug non traçable (révision amont inconnue, patchs partiellement documentés) alors que l'amont est en maintenance
  • Fichiers géants (lib.rs, instrument_registry.rs, sound_editor.rs, grid.rs) et travail recalculé à chaque image dans le thread UI
