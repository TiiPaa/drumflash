Pour le pilotage

Ce qu'il faut retenir

▲ Le risque principal, en clair

Dans un plugin audio, le « thread audio » doit rendre le son sans jamais s'interrompre. La règle d'or (écrite noir sur blanc dans la doc du projet) interdit d'y poser un verrou ou d'y réserver de la mémoire, car cela peut geler le rendu quelques millisecondes — assez pour produire un craquement audible voire faire décrocher le DAW.

L'audit a trouvé les deux à la fois : des verrous Mutex et des allocations mémoire s'exécutent dans ce thread, dont certains automatiquement pendant la lecture (mode song) et à chaque changement d'instrument. C'est le seul point classé critique.

✓ Ce qui est déjà bien tenu

  • La boucle de rendu échantillon par échantillon, elle, est propre (sans allocation ni verrou) : le problème est localisé, pas systémique.
  • 106 tests couvrent le timing, la sauvegarde/restauration et les anti-craquements — un vrai filet de sécurité.
  • Conception « data-driven » claire et aucun secret dans le code.

Critiquecodelib.rs:2750 · 1981 · 1954
Verrous Mutex bloquants sur le thread audio (mode song, chargement, sauvegarde)

Impact Viole la règle interne « no blocking locks in the audio thread » (AGENTS.md L172). Si l'UI détient le verrou de la banque de patterns pendant que l'audio le demande, le rendu se bloque → craquement, voire décrochage (xrun). Le mode song déclenche ce verrou automatiquement à chaque bouclage. Aggravant : la sauvegarde alloue aussi de la mémoire dans ce thread.

Correction Utiliser try_lock() avec report au bloc suivant, ou une file lock-free (SPSC) UI→audio + double-buffer atomique pour la banque de patterns.

Vue d'ensemble

Architecture & infrastructure

◆ Points forts d'architecture

  • Séparation nette UI / audio, état partagé lock-free dans la boucle de rendu.
  • Registre d'instruments « source unique de vérité » — ajout d'instrument = édition de données.
  • Migrations de sauvegarde versionnées et testées.

◆ Points faibles

  • Verrous/allocations dans le thread audio (voir constat critique).
  • Double indexation « slot / voix », source récurrente de bugs.
  • Fichiers géants et code d'échafaudage mort.

▸ Infrastructure

  • Livrable : un unique bundle VST3 chargé par un DAW. Aucun réseau, base de données ni secret.
  • Build : script PowerShell manuel (compile, assemble, installe). Aucune CI/CD.
  • Monitoring : aucun (normal pour un plugin desktop) ; identifiant de build affiché dans l'UI.

▸ Résilience

  • panic = "abort" : tout panic dans le rendu fait tomber le DAW hôte.
  • Contention possible du verrou de banque entre UI et audio.
  • Pas de sauvegarde hors état de projet du DAW.

À préserver

Points positifs

  • Discipline temps-réel exemplaire dans le hot path : la boucle de rendu échantillon par échantillon n'alloue pas et ne verrouille pas — état lock-free, file de déclenchements pré-allouée, types copiables. Le problème critique est en périphérie, pas au cœur.
  • Suite de tests solide (106 tests) : timing du séquenceur (dérive, swing, polyrythmie), round-trips et migrations de sauvegarde, anti-craquement du kick, tests de charge longue durée.
  • Conception data-driven propre : registre d'instruments unique, UI générée depuis les données, pas de dispatch dynamique dans le moteur audio.
  • Aucun secret en dur, dépendances minimales et ciblées, invariants critiques documentés (AGENTS.md, guides, handoffs de session).
