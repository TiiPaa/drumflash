À retravailler

Base de code saine et disciplinée sur le temps réel, mais trois chantiers structurels doivent être adressés avant de considérer le plugin comme finalisé : une allocation mémoire subsiste sur le thread audio, des panics peuvent faire planter le DAW hôte, et aucune intégration continue ne sécurise les livraisons.

Résumé pour décideur

Ce que c'est. Flash Drum est un instrument virtuel (plugin VST3) utilisé dans le logiciel de musique Studio One : un séquenceur de batterie de 64 pas avec 13 sons de synthèse, des réglages par pas et un export MIDI. Produit local, sans cloud, sans abonnement, sans données personnelles.

État de santé. Le moteur audio est de très bonne facture : il respecte les contraintes strictes du temps réel (aucune coupure sonore liée à l'architecture) et il est couvert par 276 tests automatisés. Aucune faille de sécurité exploitable à distance : le plugin ne communique avec aucun service externe.

Risques principaux. (1) Un ajout de piste pendant la lecture peut provoquer un micro-glitch sonore ; (2) dans de rares cas, une erreur interne peut fermer Studio One sans sauvegarde ; (3) l'absence de pipeline automatique fait reposer la qualité sur des vérifications manuelles.

Recommandation. Corriger les 3 actions prioritaires ci-dessous (estimé : quelques jours de développement), puis industrialiser le build. Les « gains rapides » sont faisables en moins de 30 minutes chacun.

Points forts du projet

  • Discipline temps réel exemplaire — la boucle audio ne contient ni allocation, ni verrou bloquant, ni panic ; vérifié par lecture complète du chemin process().
  • Architecture lock-free cohérente — pattern partagé, réglages et locks par pas 100 % atomiques ; état song via file SPSC ; banque de patterns en try_lock avec repli propre.
  • Persistance robuste et rétro-compatible — migrations automatiques des anciens formats (pattern-v1…v5), identifiant VST3 figé pour préserver les projets existants.
  • Couverture de tests sérieuse pour un plugin audio — 276 tests : unitaires, intégration, stress de timing et de stabilité longue session.
  • Isolation du code à risque — tout le code Windows à bas niveau (drag-and-drop OLE) vit dans un petit processus séparé, jamais dans le DAW.
  • Documentation d'invariants réellement suivie — le guide d'architecture (AGENTS.md) décrit des règles que le code respecte effectivement.

Architecture (vue expert)

Composants principaux

  • lib.rs (~150 KB) — entrée plugin, paramètres, process(), migration d'état
  • ui.rs (~308 KB, ~8000 lignes) — éditeur egui complet
  • sequencer/ — moteur 64 pas, grille lock-free
  • synthesis/ — 13 voix DSP + primitives
  • plock.rs — parameter locks par pas
  • pattern_bank.rs — slots P1-P8 + song
  • atomic_song.rs — file SPSC UI→audio
  • generator/ — 4 générateurs de patterns
  • vendor/nih-plug — fork patché (multi-out, état)

Flux de données

  • UI → audio : atomiques + file SPSC (patterns, song, réglages)
  • Audio → DAW : mix principal + 14 sorties auxiliaires stéréo + notes MIDI canal 10
  • UI → disque : config.json, exports .mid, dumps de presets
  • UI → OS : processus helper de drag-and-drop MIDI
  • DAW ↔ plugin : état persisté (pattern-v5, sound-settings-v2, plock-v1)

Patterns détectés

  • Temps réel strict (no-alloc / no-lock / no-panic)
  • Producteur-consommateur SPSC lock-free
  • Persistance versionnée avec migrations
  • Vendoring de dépendance patchée

Infrastructure

Modèle. Projet 100 % local : compilation sur le poste du développeur (Windows) via build.ps1, installation par copie dans le dossier système VST3, validation manuelle dans Studio One. Aucun serveur, aucune base de données, aucun service tiers à l'exécution, aucun secret à gérer. Le code source est hébergé sur GitHub.

  • Déploiement — manuel : cargo build --release → bundle .vst3 → copie dans C:\Program Files\Common Files\VST3. Aucune CI/CD.
  • Observabilité — logs dans le DAW (debug), build ID horodaté affiché dans l'UI, checklists de validation manuelle dans le CHANGELOG. Pas de métrique ni d'alerte.
  • Résilience — l'état musical vit dans le projet du DAW (migrations assurées) ; pas de backup automatisé ; point de défaillance unique = le poste de développement.
  • Scalabilité — non applicable (plugin local) ; limites internes (14 slots, 64 pas) couvertes par des stress tests.
